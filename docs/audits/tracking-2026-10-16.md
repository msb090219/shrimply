# Tracking fixes and first verification pass

Date: 16 October 2026. Local Windows 11 build 26200, Python 3.13.5,
PyInstaller 6.22.3. These results apply to this machine and camera 0.

Automated baseline: **87 tests passed**, including 27 added regression/tool checks.

## Implemented

- T01: Usable returning detections raise the Away sampling rate before smoothing,
  so the three-frame window can fill. Regression uses the actual controller,
  smoother, and inference-rate policy with an injected clock.
- T02: Device changes preserve manual pause and idle-stop. Rescan preserves the
  selected device without emitting camera-change signals. Regression also checks
  that resuming opens the device selected while paused.
- T03: Worker restarts wait for the previous worker's finished signal. Pause,
  restart, and quit do not block the UI waiting for capture. Stop interrupts rate
  and retry waits. Capture/inference exceptions notify the controller and resources
  are released on exit. Partial model construction releases the first model.
- T04: Contradictory signal ordering is excluded. Verification limits tolerance
  widening so the measured hunch remains at or above the default bad threshold.
- T05: Verification requires observations across the interval, with no gap over
  two seconds, instead of accepting one frame.
- T07: Drifting and missing observations interrupt sustained-good recovery.
- Additional fixes: startup absence can reach Away; skipping setup displays the
  tall instruction; calibration can start from pause and retains preview after a
  worker restart. Camera failures clear stale mascot feedback.

Pending camera shutdown is labelled `stopping camera`; the physical camera light
has not been verified. These changes do not fix history accounting, config/baseline
validation, landmark confidence, single-instance protection, or every audit item.
Use a fresh calibration for controlled testing; existing saved calibrations were
not rewritten or invalidated.

## Still requires supervised testing

The guided session began after the automated checks. Calibration attempts at
19:09:07 and 19:11:55 local time failed the separation check. The user interpreted
the first return to tracking as success; the saved baseline remained dated
12 October. The planned normal-sitting check was stopped to avoid measuring
against that old baseline.

This exposed a calibration-outcome communication problem. Fixed afterward:
failure now displays a persistent dialog stating that calibration was not saved
and whether the previous baseline remains active. Added numeric per-phase
calibration diagnostics and two regression tests. These follow-up changes were
tested in a source launch, then included in a rebuilt executable. That executable
passed `diagnostics/packaged-calibration-fix-smoke.json` with `frozen: true`.

The instrumented source run calibrated successfully at 19:15:22, with all setup
checks passing, 24 verification samples, and tolerance tuning of approximately
1.17. An initial interval afterward was unlabelled because the user could not
confirm what posture they were holding; it is not evidence of a false positive.

The user then explicitly confirmed normal sitting before a timed hold. In the
60-second window 19:18:50–19:19:50 (end exclusive), 115 scorable samples contained
103 good and 12 drifting classifications, with **no bad classifications**. The
maximum deviation was 1.1185. These are sample counts, not time percentages.
This establishes one normal-sitting case without bad-state reminders; it does
not establish general accuracy. The original numeric log and extracted window
are retained locally under `diagnostics/` and the app's diagnostic-log directory.

After a later explicit Ready response, the slouch hold ran for 55 seconds from
20:43:05. Its window contained 179 scorable samples (181 total): 178 reported bad,
one drifting, and two held the previous good state while unscorable. Mean scored
deviation was 1.7393, maximum 1.9307. The user confirmed seeing the floating shrimp.
This confirms the visual cue, not whether a Windows notification toast appeared.

The recorded state returned to good at 20:44:07. Replaying the numeric scores
through the current state machine inferred an alert at 20:44:00 and sustained-good
recovery at 20:44:18. The replay omitted the earlier manual pause/resume actions,
causing two warmup-state mismatches before the hold; the hold's subsequent states
matched. These inferred events are not direct proof of OS notification delivery.
The recovery instruction's marker was written after the chat instruction, so no
precise physical-movement-to-recovery latency is claimed.

Resource tools recorded the packaged session briefly, then 114 source-session
samples over approximately ten minutes (`diagnostics/guided-source-resources.csv`).
Working set changed from 380.79 MB to 213.27 MB, private memory from 772.59 MB to
667.64 MB, handles from 2374 to 2193, and threads from 134 to 26. The log records a
manual pause at 19:22:52; 31 samples after 19:23:00 averaged 0.136% of one CPU core.
This supports reduced activity after pause. It does not establish working-day
stability, battery use, or the timing of the physical camera indicator. A package
build also ran during part of the session, so CPU observations were not isolated.

## Controlled leave and return

The user confirmed readiness, moved out of camera view, and was prompted to
return after a 25-second wait. The log entered Away at 21:12:12. The first usable
returning detection arrived at 21:12:41; scoring resumed at 21:12:43, approximately
2.490 seconds after that detection. Returning movement initially scored bad,
then drifting, before reaching Good at 21:12:49. Away sampling was 0.5 fps and
the rate increased on return. This single camera-0 case confirms that the app
did not remain stuck in Away. It does not measure the delay from the person's
physical return, which was not independently timestamped.

Numeric evidence: `diagnostics/away-return-summary.json` and the session's
original diagnostic log. A manual camera-light check on Pause was requested next.
